# Estado del proyecto — TiendaYa

> Última actualización: 2026-10-23. Este documento resume qué se construyó, qué se decidió y qué falta, para que cualquiera (o una sesión futura) pueda retomar el proyecto sin releer todo el historial. El detalle técnico vive en los ADR y en [ERD-ARQUITECTURA-POLIGLOTA.md](ERD-ARQUITECTURA-POLIGLOTA.md). Las comprobaciones históricas conservan sus fechas; la evidencia de Cassandra está registrada en §3.10 y ADR-004 §9.

## 1. Resumen ejecutivo

La **Fase Inicial** del PRD está completa y verificada de punta a punta: esquema relacional normalizado, ERD documentado, checkout como transacción atómica, DDL versionado y datos de prueba. Sobre esa base ya se construyó bastante más de lo mínimo: backend completo (auth, catálogo con atributos variables por categoría, pedidos) y un frontend funcional (tienda + panel de vendedor).

El catálogo descriptivo y su historial ya viven en **MongoDB**; MySQL conserva la autoridad transaccional. **Redis** resuelve carrito, ofertas limitadas y recomendaciones. El panel de ventas por intervalos está implementado sobre **Cassandra**, reemplazando la propuesta preliminar de Neo4j ([ADR-004](ADR-004-analitica-ventas-cassandra.md)). El contenedor está saludable, la carga histórica está conciliada y las 17 pruebas aisladas pasaron; ver §3.10 para los límites de validación.

## 3. Qué se construyó

### 3.1 Backend — núcleo de la Fase Inicial (registro histórico)

Esta subsección conserva el punto de partida relacional. Las tablas de catálogo citadas abajo se retiraron después (§3.5); el modelo vigente, incluida la incorporación de outbox, está en `prisma/schema.prisma` y ERD-ARQUITECTURA-POLIGLOTA.md.

- **Esquema relacional** (`backend/prisma/schema.prisma`): 15 entidades — usuarios, rol_usuario, direcciones, metodo_pago, categoria, subcategoria, producto, inventario, atributo_categoria, atributo_producto, categoria_producto, carrito, compra, pago, compra_detalle. Basado en la Página 1 del ERD original, confirmada como base (ver [ERD.md](ERD.md) §0).
- **4 migraciones versionadas** en `backend/prisma/migrations/`: esquema inicial, `id_vendedor` en producto, `cantidad` en compra_detalle, restricción unique en atributo_producto.
- **MySQL en Docker** (`docker-compose.yml` + `docker/mysql-init/`), con el grant de permisos que necesita Prisma Migrate para su shadow database.
- **`prisma/seed.js`**: datos de prueba representativos (roles, usuarios, categorías → subcategorías → atributos, productos con inventario y valores de atributo).
- **Checkout atómico** (`src/services/checkoutService.js`): pedido + líneas + pago + descuento de inventario en una única transacción de Prisma. Verificado con `npm run verificar:checkout` (compra válida + intento de sobreventa rechazado sin dejar el inventario a medio actualizar) y por HTTP real.

### 3.2 Backend — funcionalidad agregada sobre la base

| Área | Qué incluye |
|---|---|
| **Auth** (`authService.js`, `middleware/auth.js`) | Registro (valida formato de correo, contraseña ≥8 caracteres, siempre asigna rol `comprador`), login (JWT con rol incluido), `GET /api/auth/me`. Middlewares `requireAuth` y `requireRole`. |
| **Direcciones / métodos de pago** | CRUD propio del usuario autenticado, con UI completa en `/cuenta` (`AccountPage.jsx`) — listar, crear y **borrar**, ambos formularios compartidos con Checkout (`components/account/`). La tarjeta nunca se guarda completa — solo `token_pasarela` + últimos 4 dígitos + marca (ver ERD.md 1.4.2). Borrar algo referenciado por un pedido ya hecho da `409` con mensaje claro en vez de dejar pasar el error crudo de Prisma (ver §4). |
| **Catálogo** (`categoriaService.js`, `productoService.js`) | Categoría → subcategoría → atributo (navegación pública, alta restringida a `vendedor`/`administrador`). Productos: listado con filtros (`categoriaId`, `subcategoriaId`, `q` de texto simple, `vendedorId`), detalle, alta y edición (un `vendedor` solo edita lo suyo, `administrador` edita cualquier producto). |
| **Checkout** | Valida que la dirección y el método de pago pertenezcan a quien paga, y que las cantidades sean enteros positivos (antes una cantidad negativa pasaba la validación de stock y *sumaba* inventario en vez de restarlo). |
| **Pedidos** (`compraService.js`) | Historial propio (`GET /api/compras`) y detalle (`GET /api/compras/:id`), nunca el de otro usuario. |

### 3.3 Frontend — tienda (`frontend/`)

React (JS) + Vite + React Router + Tailwind CSS v4. Layout inspirado en Amazon (header oscuro, buscador prominente, grilla de productos) con una paleta propia basada en teoría del color — azul para confianza/calma como color principal, verde azulado como acento de acción positiva, deliberadamente distinta del naranja de Amazon (que comunica urgencia). Paleta y justificación en `frontend/src/index.css`.

Páginas: catálogo con búsqueda/filtro por categoría (incluye un menú desplegable de categorías pegado a la barra de búsqueda — cada categoría se puede expandir in situ para ver y elegir directamente una subcategoría, p. ej. Electrónica ▸ Celulares, sin pasar primero por la página de la categoría completa) y **filtro facetado por atributo** dentro de una subcategoría (sidebar de checkboxes — RAM, color, talla, lo que aplique; ver abajo), detalle de producto, carrito (vive en `localStorage`, no en el backend — ver §5), login/registro, checkout (selección o alta de dirección/método de pago), historial y detalle de pedidos, cuenta (direcciones/métodos de pago). Responsive verificado en mobile/tablet/desktop sin desbordes horizontales.

**Filtro por atributo** (`HomePage.jsx`): a diferencia de `?q=` (que solo busca en `descripcion`, ver ADR-002), esto filtra por el valor exacto de un atributo — `productoService.listar()` acepta `?atributos=<JSON {nombre:valor}>` y arma un `$elemMatch` por par (todos exigidos a la vez, con `$and`, porque cada par tiene que matchear un elemento distinto del array). El sidebar solo aparece dentro de una subcategoría (los atributos no tienen sentido a nivel "todos los productos" o una categoría con varias subcategorías); las opciones se calculan en el cliente a partir del catálogo completo de esa subcategoría, no de una agregación aparte del backend, y no se recalculan a medida que se marcan casillas (simplificación consciente, no una limitación descubierta después — ver README).

**Filtro por precio + orden "Más vendidos"** (`HomePage.jsx`, siempre visible, no atado a una subcategoría — a diferencia de los atributos, el precio existe para cualquier producto): filtra directo sobre `Producto.precio` en Mongo (copia de lectura reenviada desde `inventario`/MySQL, ver ADR-002 §3.3 — al momento de construir este filtro todavía no existía esa copia y se resolvía cruzando a MySQL primero; eso ya no aplica). "Más vendidos" ordena por `total_vendido`, un campo en `Producto` (Mongo) que es una **caché de solo lectura** de `compra_detalle.cantidad` (MySQL) — mismo patrón que `vendedor_nombre` (ver ADR-002 §6.3): nunca se lee la base relacional al navegar el catálogo, solo se actualiza ahí cuando una compra se confirma. Tiene su propio índice compuesto `{subcategoria_id, total_vendido}` en `Producto.js` (y precio el suyo, `{subcategoria_id, precio}`), mismo patrón que `{producto_id, fecha}` en `ProductoEvento.js`. El campo se actualiza en `checkoutService.checkout()` (después de que la transacción de MySQL ya se confirmó, nunca dentro de ella) y se puede recalcular desde cero con `POST /api/admin/recalcular-ventas` si alguna vez se desincroniza — reconciliación que sobrescribe, ver `catalogoSyncService.js`.

### 3.4 Frontend — panel de vendedor (`frontend/src/pages/seller/`)

Visible solo para cuentas `vendedor`/`administrador` (link "Mi tienda" en el header). Dashboard con los productos propios; formulario de alta/edición que permite crear categoría → subcategoría → atributo sobre la marcha si todavía no existen, con los campos de valor de atributo generados dinámicamente según la subcategoría elegida. Al editar, la categoría queda fija (recategorizar no está soportado — hay que publicar un producto nuevo).

**Historial por producto, directo desde la lista** (`SellerDashboardPage.jsx`): cada fila tiene un botón "Historial" que despliega el mismo `HistorialSection` de `ProductDetailPage.jsx` — línea de tiempo clickeable + `SnapshotPreviewCard` — inline, debajo de esa fila (uno a la vez). Sin re-chequeo de rol acá: `/vendedor` ya está detrás de `RequireRole`, así que quien ve el dashboard ya tiene permiso. Esto obligó a sacar `HistorialSection`/`SnapshotPreviewCard` de `ProductDetailPage.jsx` a un componente compartido (`frontend/src/components/product/HistorialSection.jsx`) para no duplicar ~190 líneas — mismo patrón ya usado con los formularios de dirección/método de pago (`components/account/`, ver §3.2).

**Renombrar/quitar un atributo de un producto puntual** (`SellerProductFormPage.jsx`): cada atributo se edita ahora en una fila con dos campos igual de editables — "Nombre del atributo" (antes era una etiqueta fija, no interactiva — el pedido original del usuario fue justamente que intentaba tocar ese texto y no pasaba nada) y "Valor" — más un link "Quitar" que vacía la fila entera. Renombrar (p. ej. "Almacenamiento" → "Memoria") conserva el valor que ya tenía cargado, sin pasar por "+ Crear nueva" ni volver a tipearlo. Por debajo sigue siendo un reemplazo, no una edición in-place de la definición: el nombre nuevo se manda junto con el valor vigente en el array completo de `atributos` del producto; el nombre viejo no se borra de la plantilla de la subcategoría (otros productos pueden seguir usándolo) y vuelve a aparecer como campo vacío la próxima vez que se carga el formulario. Esto requirió el mismo cambio de fondo que "Quitar": `productoService.actualizar()` trataba `atributos` como *merge* (actualiza o agrega, nunca borra), así que vaciar o renombrar un campo y guardar no tenía ningún efecto — el valor viejo seguía ahí. Se cambió a reemplazo completo, disparado por `atributos !== undefined` (antes exigía además `.length`, así que mandar un array vacío ni siquiera entraba al bloque). Agregado también un chequeo de nombres duplicados (frontend, antes de enviar, y backend como defensa adicional) — necesario porque con nombre editable es fácil terminar con dos filas apuntando al mismo nombre sin querer. No toca `atributos_definidos` de la subcategoría (seguir sin poder borrar/renombrar una definición de atributo *para todos los productos a la vez* es una limitación conocida, ver §5) — es estrictamente a nivel de qué atributos tiene *este* producto. Un solo componente de formulario detrás de `/vendedor/productos/:id/editar` y `/admin/productos/:id/editar`, así que cubre ambos roles. Verificado en vivo: renombrar Almacenamiento→Memoria conservando "128GB" (confirmado por API), intento de colisión de nombres bloqueado con mensaje claro sin llegar al backend, y reversión Memoria→Almacenamiento — confirmado por API en cada paso.

### 3.5 Entrega 1 — implementación (MongoDB)

Modelo dividido (ver [ADR-002 §3.2](ADR-002-migracion-catalogo-documental.md#32-actualización-2026-08-23-por-qué-preciocantidad-no-migran)): `categoria`, `subcategoria` y el contenido descriptivo de `producto` (descripción, estado, atributos, imágenes) viven en MongoDB; `precio`/`cantidad` tienen a `inventario` (MySQL) como única fuente transaccional, sin cambios en eso — pero desde el 2026-08-29 también se guarda una copia de lectura en Mongo (ver [ADR-002 §3.3](ADR-002-migracion-catalogo-documental.md#33-actualización-2026-08-29-copia-de-lectura-de-preciocantidad-en-mongo) y el punto de abajo), para no romper la atomicidad del checkout.

- **MongoDB**: contenedor en `docker-compose.yml` como replica set de un nodo (`rs0`) — se auto-inicializa vía el healthcheck. Mongoose como ODM (misma naturaleza de decisión que Prisma vs. Sequelize).
- **ETL** (`backend/scripts/etlCatalogoAMongo.js`): migra `categoria`/`subcategoria`/`producto` a Mongo, reproducible (limpia las colecciones destino antes de escribir). Corrido y verificado contra los datos reales del proyecto.
- **`categoriaService.js` y `productoService.js`** reescritos contra Mongo (las lecturas ya no combinan con `inventario`/MySQL, ver el punto de precio/cantidad más abajo). El contrato de API se mantuvo lo más parecido posible al anterior; lo que cambió de forma (atributos, ids de categoría, vendedor) obligó a actualizar `ProductDetailPage`, `SellerDashboardPage` y `SellerProductFormPage` en el frontend.
- **`Producto` (Mongo) ahora guarda `precio`/`cantidad` como copia de lectura** (2026-08-29, ver [ADR-002 §3.3](ADR-002-migracion-catalogo-documental.md#33-actualización-2026-08-29-copia-de-lectura-de-preciocantidad-en-mongo)) — `inventario` (MySQL) sigue siendo la única fuente transaccional, checkout no cambió una línea. Lo que cambió es que `productoService.actualizar()`/`crear()` y `checkoutService.js` reenvían el valor vigente a Mongo después de cada escritura en MySQL (mismo patrón que `vendedor_nombre`/`total_vendido`), así que `listar()`/`obtener()` ya no cruzan a MySQL para nada — el filtro de precio (`?precioMin=`/`?precioMax=`) pasó de "resolver en MySQL, pasar ids a Mongo" a un filtro directo de Mongo con su propio índice `{subcategoria_id, precio}`. Los documentos que ya existían en Mongo antes de este cambio se rellenaron con `POST /api/admin/recalcular-inventario` (mismo mecanismo que `recalcular-ventas`, corrido una vez sobre los datos reales del proyecto — 5 de 5 productos actualizados). Verificado en vivo: filtro de precio y "más vendidos" devolviendo los valores correctos desde Mongo, una edición de precio propagándose (confirmado por API), y `verificar:checkout` completo mostrando el stock descontado igual en MySQL y en Mongo (45→43 en ambos) tras una compra real.
- **Las columnas vestigiales de `producto` en MySQL (`descripcion`/`imagen_url`/`estado`) dejaron de mantenerse en sync** (2026-08-29) — `productoService.actualizar()` ya no las reescribe en cada edición. Antes se sincronizaban "por las dudas" aunque Mongo ya era la fuente de verdad; ahora esa fila de MySQL se conserva solo como ancla de FK para `inventario`/`compra_detalle`/`carrito`, sin que ninguna lógica la toque para lo descriptivo. Las otras tablas vestigiales (`categoria`, `subcategoria`, `atributo_categoria`, `atributo_producto`, `categoria_producto`) ya estaban en ese mismo estado — se confirmó por grep que ningún código vivo (fuera de `seed.js` y el ETL de bootstrap) las escribía.
- **Esas tablas vestigiales se borraron al día siguiente** (2026-08-30, ver [ADR-002 §3.4](ADR-002-migracion-catalogo-documental.md#34-actualización-2026-08-30-se-borra-el-catálogo-relacional-vestigial)): `categoria`, `subcategoria`, `atributo_categoria`, `atributo_producto`, `categoria_producto`, y las columnas descriptivas de `producto` — migración `20260830000000_drop_catalogo_relacional_vestigial`, verificada antes de aplicar (Mongo tenía todo lo que MySQL tenía, más una subcategoría/atributo que MySQL nunca llegó a ver) y probada de punta a punta contra una base descartable antes de tocar la real. `producto` sigue existiendo como ancla de FK — solo perdió las columnas que ya no eran fuente de verdad de nada. Esto dejó sin sentido dos piezas más, que se borraron con ella: `scripts/etlCatalogoAMongo.js` (nada de qué hacer ETL sin las tablas relacionales — su trabajo se absorbió en `prisma/seed.js`, que ahora puebla MySQL y Mongo en un solo paso) y `catalogoSyncService.sincronizarFaltantes()`/`POST /api/admin/sync-catalogo` (backfillear Mongo desde tablas que ya no existen es imposible). `recalcularVentas`/`recalcularInventario` y sus rutas no se tocaron — leen `compra_detalle`/`inventario`, que siguen en MySQL.
- **`precio`/`cantidad` pasaron de campos sueltos a `inventario: {precio, cantidad}` anidado en Mongo** (2026-08-30, ver [ADR-002 §3.6](ADR-002-migracion-catalogo-documental.md#36-actualización-2026-08-30-preciocantidad-anidados-como-inventario-en-mongo)) — cambio de forma, no de arquitectura, para que coincida con la forma que `snapshot.inventario` ya usaba en el historial de cambios desde que existe. Migración de datos única sobre los 5 productos reales del proyecto (mover los campos sueltos al objeto anidado). Se encontró y corrigió al mismo tiempo un bug preexistente no relacionado: `productoService.crear()` seguía intentando escribir `descripcion`/`imagen_url`/`estado` en MySQL, columnas que ya no existían ahí desde el punto anterior — nadie lo había notado porque ningún producto nuevo se había creado después de esa migración, solo editado los existentes.
- **Historial de cambios por eventos** (`ProductoEvento`, ver [ADR-003](ADR-003-historial-cambios-eventos.md)): cada alta/edición agrega un evento con snapshot completo, nunca sobrescribe. `GET /api/productos/:id/historial?fecha=` reconstruye el estado vigente en cualquier fecha. **Con UI**: `ProductDetailPage.jsx` muestra la línea de tiempo completa (tipo, versión, quién editó, campos modificados) y un formulario para consultar el estado en una fecha arbitraria — antes de esto el requerimiento solo era comprobable por curl, sin superficie en la app real (encontrado en una auditoría de qué funciones del backend no tenían frontend consumiéndolas).
- **El historial ahora versiona precio/cantidad además de lo descriptivo** — decisión revisada sobre el planteo original de ADR-003 §3.1 (que explícitamente los dejaba afuera). `actualizar()` ya no exige un cambio descriptivo para generar un evento: un edit de *solo* precio o *solo* cantidad también crea uno, con `campos_modificados: ['precio']`/`['cantidad']` y el snapshot completo (`inventario: {precio, cantidad}` incluido siempre, aunque esta llamada puntual no los haya tocado — mismo principio de "snapshot completo, no delta" que ya regía). A propósito **no** incluye los descuentos de inventario del checkout — eso seguiría siendo cada venta, y convertiría el historial de catálogo en un libro de ventas. `GET /:id/historial` pasó a requerir `vendedor`/`administrador` (antes era público) porque ahora expone precio histórico y patrones de stock, información de negocio que un comprador no debería poder curiosear — `HistorialSection` en el frontend solo se monta si el rol del usuario logueado es uno de esos dos.
- **"Ver estado en una fecha" ahora muestra una mini-tarjeta con pinta de catálogo** (`SnapshotPreviewCard` en `ProductDetailPage.jsx`) en vez de texto plano — mismo lenguaje visual que `ProductCard.jsx` (imagen, precio, badge de stock/agotado), pero deliberadamente **sin botón de "Agregar al carrito"**: es una vista de solo lectura de un momento pasado, comprar "esa versión" no tiene sentido (el id sigue siendo el del producto actual). `vendedor_nombre`/subcategoría no están en el snapshot (no se versionan, ver ADR-003 §3.1) — se toman del producto vigente, que es información estable (no se puede recategorizar ni cambiar de dueño). Maneja bien snapshots viejos sin `inventario` (anteriores a que se empezara a versionar precio/stock) con un mensaje explicativo en vez de romperse.
- **Cada entrada de la línea de tiempo también es clickeable** y muestra esa `SnapshotPreviewCard` directamente, sin pasar por el buscador de fecha — necesario porque ese buscador solo tiene granularidad de día (`?fecha=AAAA-MM-DD`, sin hora): si un producto tuvo dos ediciones el mismo día (pasó de verdad probando esto — precio y estado editados minutos aparte), buscar por esa fecha solo puede devolver la última versión del día, nunca la de en medio. El click no pide nada nuevo al backend — el snapshot de cada evento ya viene con la línea de tiempo completa (`GET /:id/historial` sin `?fecha=`), así que es instantáneo. La entrada seleccionada queda resaltada.
- **Índice compuesto** `{producto_id, fecha}` sobre `producto_eventos` — confirmado creado, no solo declarado.

### 3.7 Entrega 2 — carrito en Redis (`cartService.js`, `cartRoutes.js`, `CartContext.jsx`)

> **Actualización 2026-10-03:** el carrito es durable en MySQL (`carrito`, único por usuario/producto). Redis conserva su propia copia del producto (id, descripción, imagen, estado y precio), cantidad solicitada y disponibilidad revisada, sin cantidad de inventario. Formato 3, TTL de 450s por inactividad. Abrirlo con caché vigente solo consulta Redis; al faltar/vencer se reconstruye con cantidades SQL y datos Mongo/SQL por lote. Entrar al checkout llama `POST /api/carrito/revisar`, reemplaza las copias y muestra únicamente los datos vigentes. Al confirmar se comprueban productos activos y precio/stock otra vez; el rechazo provoca una nueva revisión. Se eliminó el resumen compartido. Lua con revisión por usuario evita publicaciones viejas tras una mutación/checkout. El pedido borra SQL en su transacción e invalida Redis tras el commit. Diseño y límites en [README](../README.md#cambios-de-carrito-y-caché--2026-10-03). Los puntos fechados abajo describen la implementación histórica de 2026-08-30.

**Verificación del cambio:** 18 pruebas aisladas Redis y 19 de ventas aprobadas. La integración real por HTTP/JWT verifica lectura caliente sin SQL/Mongo, TTL efectivo, revisión actualizada y concurrencia flash con datos sintéticos exclusivos; conserva los pedidos. Evidencia en README. Build aprobado, lint sin errores y con advertencias React existentes. Sin inspección visual del navegador ni benchmark de latencia.

Primera pieza de Entrega 2 implementada — plan completo en [ENTREGA-2-PLAN.md §4.1](ENTREGA-2-PLAN.md#41-carrito-en-redis-implementado-y-verificado-2026-08-30).

- **Infra:** servicio `redis` en `docker-compose.yml` (imagen `redis:7`, sin volumen — dato transitorio a propósito, no hace falta persistirlo), `ioredis` como dependencia, `backend/src/config/redis.js` (conexión perezosa, mismo patrón que `config/mongo.js`).
- **El carrito ahora requiere sesión iniciada** — dejó de ser anónimo/de navegador. Se clave por `carrito:{usuario.id_usuario}` (hash de Redis, `productoId → cantidad`), no por una cookie de sesión separada. Consecuencia directa y verificada: el carrito **persiste a través de un logout→login** (no estaba en el plan original, se confirmó al probar) — un beneficio real de clavear por identidad de usuario en vez de por sesión de navegador.
- **TTL de 7.5 minutos (450s) por inactividad**, reiniciado en *cualquier* interacción — incluida una simple lectura del carrito, no solo agregar/quitar. `EXPIRE` se reemite en cada operación de `cartService.js`, nunca se pone una sola vez.
- **`agregar()` clampa contra el stock vigente** (`Producto.inventario.cantidad` de Mongo) — mismo comportamiento que ya tenía el carrito viejo del lado del cliente, ahora verificado del lado del servidor (no se puede eludir mandando una cantidad enorme directo a la API).
- **El checkout vacía el carrito del lado del servidor**, dentro de `checkoutService.checkout()` mismo, no solo cuando el cliente lo pide aparte después de una respuesta exitosa — encontrado como gap real al escribir la verificación: si esa segunda llamada del cliente nunca llegaba (pestaña cerrada justo después de pagar), el carrito seguía mostrando algo ya comprado. Ahora es un efecto garantizado del checkout mismo (con su propio try/catch, best-effort, igual que el resto de las escrituras cruzadas de este proyecto — ver ADR-002 §5); el frontend también lo pide aparte, de forma redundante.
- **Frontend:** `CartContext.jsx` mantuvo su interfaz pública exacta (`items`, `agregar`, `actualizarCantidad`, `quitar`, `vaciar`, `cantidadTotal`, `total`) para no tener que tocar `Header.jsx`/`ProductCard.jsx`/`CheckoutPage.jsx` — internamente pasó de mutar `localStorage` de forma síncrona a llamar la API de forma async. Un visitante sin sesión que hace clic en "Agregar al carrito" se redirige a `/login?next=...` (mismo destino que usa `RequireAuth.jsx` para rutas completas, acá como chequeo inline porque el botón vive en páginas públicas). `agregar()` ahora devuelve si de verdad agregó algo, para que "Comprar ahora" (que navega a `/carrito` después) no navegue igual si en realidad redirigió a login — gap real encontrado al migrar ese botón específico.
- **"Continuar donde lo dejaste" tras el redirect a login** (agregado después, a pedido): el producto que se quería agregar antes de que `agregar()` redirigiera a `/login` se guarda en `sessionStorage` (`tiendaya_carrito_pendiente` — sobrevive la navegación a `/login` y de vuelta, se limpia sola si se cierra la pestaña). El mismo `useEffect` de `CartContext.jsx` que ya reaccionaba a que apareciera `usuario` ahora revisa primero si hay algo pendiente: si lo hay, lo agrega de verdad (vía la API, no una simulación) en vez de solo traer el carrito tal cual estaba, y muestra un toast de confirmación (`components/common/Toast.jsx`, nuevo — notificación simple, auto-oculta a los 4s, sin sistema de notificaciones genérico detrás, un solo caso de uso). Se borra de `sessionStorage` **antes** de intentar el agregado, no después, para no reintentarlo en un refresh si algo falla a mitad de camino. Funciona igual después de registrarse (no solo de iniciar sesión) porque `registrar()` ya llama a `login()` internamente — la lógica reacciona a que haya `usuario`, no a por qué ruta se llegó ahí. Verificado en el navegador con Redis inspeccionado directamente en cada paso (para no depender de capturar el toast a tiempo entre llamadas de herramienta): el pendiente se guarda al redirigir, se limpia al iniciar sesión, el ítem aparece en Redis con la cantidad correcta, y el texto del toast confirmado en el DOM.
- **Verificación:** `npm run verificar:carrito` (`backend/scripts/verificarCarrito.js`, mismo espíritu que `verificar:checkout`) cubre agregar+TTL inicial, reinicio de TTL en una interacción posterior, clamp contra stock, borrado de la clave al quitar el último ítem, y vaciado del carrito tras un checkout real — las 5 verificaciones pasan contra los datos reales del proyecto. Probado también a mano en el navegador: agregar sin sesión (redirige a login), agregar con sesión, actualizar cantidad, checkout completo (carrito vacío después, stock descontado, orden visible en `/pedidos`), y persistencia a través de logout/login.
- **Regla: nadie compra lo que él mismo vende (2026-10-04).** `productoService.verificarNoEsPropio(usuarioId, productoIds)` rechaza con **403** ("No podés comprar tus propios productos") si algún producto tiene `id_vendedor = usuarioId` — consulta MySQL, la fuente transaccional, no el `vendedor_id` cacheado en Mongo. Se aplica en **todos** los caminos de compra: `checkout()` y `checkoutOferta()` (autoridad final, antes de tocar stock: un pedido mixto se rechaza completo), el carrito (`agregar`/`actualizarCantidad`, para que nunca contenga algo que el checkout va a rechazar), la oferta flash y la recomendación (antes de Redis, para no gastar cupo). Las recomendaciones además excluyen los productos del propio vendedor y la UI oculta los controles de compra (`ProductCard`, `ProductDetailPage`, `OfertasPage`). Motivo: un vendedor que se compra a sí mismo infla sus ventas y su reputación sin un cliente real (ver la Señal F de §3.11, que sigue detectando lo anterior a la regla y las compras entre cuentas distintas de una misma persona). `npm run verificar:compraPropia` prueba cada camino y que el rechazo no deja rastro (ni pedido, ni stock, ni cupo de Redis); `Elasticsearch` guarda `vendedor_id` para que la tarjeta del buscador sepa si un resultado es propio.
- **Compromiso de no reventa (2026-10-04).** Las cuentas que pueden publicar (`vendedor` y `administrador`) sí pueden comprar productos de otros vendedores, pero no revenderlos. Por eso las **tres** pantallas de compra (carrito, oferta flash y recomendación) abren, al confirmar, una ventana (`CompromisoNoReventaModal`) que dice que la cuenta se compromete a no revender y que, si lo hace, incumple los Términos de Servicio; exige marcar una casilla y no acepta nada con Escape, el fondo o "Cancelar". El servidor lo exige igual (`compromisoService.exigirCompromiso`): lee el rol de MySQL, pide `aceptaNoReventa === true` (un `"true"` o un `1` no cuentan) y responde **400** con `codigo: COMPROMISO_NO_REVENTA` — después de la regla de compra propia y **antes de tocar stock o Redis** (en flash y recomendación, antes de gastar cupo). La constancia es `compra.no_reventa_aceptada_en` (migración `20261004000000_compromiso_no_reventa`), guardada **dentro de la transacción del pedido** y nullable a propósito: los pedidos anteriores y los de compradores no tienen compromiso y no se rellena con una fecha inventada. El detalle del pedido le muestra al vendedor lo que aceptó. La detección de quien lo rompe es la Señal G de §3.11. `npm run verificar:compromisoReventa` prueba la matriz de roles y que cada camino rechaza sin dejar rastro; `npm run test:compromiso` cubre la regla aislada. Los «Términos de Servicio» del aviso son un enlace a la página pública **`/terminos`** (`TerminosPage.jsx`, ocho secciones con ancla; el aviso abre `/terminos#no-reventa` en una pestaña nueva y también la enlazan el detalle del pedido y el pie de página). El texto solo enuncia reglas que el sistema aplica o vigila de verdad, dice que los pagos son simulados y no publica umbrales de fraude; ver [PLAN-NEO4J-DETECCION-FRAUDE.md §19](PLAN-NEO4J-DETECCION-FRAUDE.md).

### 3.8 Entrega 2 — oferta flash (`ofertaFlashService.js`, `ofertaRoutes.js`, `checkoutService.checkoutOferta`)

> **Actualización 2026-10-04 (reemplaza la de 2026-10-03, que daba a los datos un TTL fijo de 60 s y los publicaba al editar):** los datos de la oferta se guardan **con la misma estructura y el mismo protocolo que el carrito** (§3.7). `oferta:{id}:datos` es un hash con `_formato` y **todo** lo que la pantalla necesita sin volver al catálogo — descripción, estado, imagen principal y galería, atributos, subcategoría, vendedor, precio normal, resumen de reseñas, versión y la configuración de la oferta (`precio_oferta`, `stock_oferta`, vigencia), un campo cada uno (los anidados, en JSON) —; lo único que no se copia es la cantidad real de inventario, que cambia con cada venta y tiene su autoridad en MySQL. `oferta:{id}:revision` es un contador sin TTL. `oferta:{id}:stock` sigue siendo el cupo en vivo, otra clave atómica e independiente: **regenerar los datos nunca la toca**. Solo se cachea mientras la oferta está **activa** (activo, producto activo y sin vencer); sin oferta, pausada o vencida se lee directo de Mongo y no ocupa nada en Redis. TTL de 450 s por inactividad, renovado en cada lectura y **sin pasar nunca de `vigente_hasta`**; además, la copia no se sirve con más de **600 s** de edad aunque se siga leyendo.
>
> **Cómo se detecta que la clave hay que regenerarla** (igual que el carrito): una sola lectura atómica (script Lua `leerOferta`) trae la revisión y todos los campos del hash y renueva el TTL. Se regenera desde Mongo si **(a)** el hash no existe — venció el TTL, Redis lo desalojó o se reinició, o un escritor lo invalidó: es la señal de "expiró" —, **(b)** su `_formato` no es el vigente (o la clave es una cadena JSON del formato anterior, que el script descarta), **(c)** falta un campo, no se puede leer o el `id` no coincide con el producto pedido, o **(d)** la copia es **demasiado vieja** — se generó hace más de 600 s aunque se siga leyendo: es la red de seguridad de una invalidación perdida, porque cada lectura renueva el TTL y el precio de oferta que se cobra sale de esta copia, que a diferencia del carrito lee todo el mundo. La regeneración publica con `publicarOferta`, que **solo escribe si la revisión sigue siendo la que se leyó**: cada edición del producto o de la oferta (`invalidar`: sube la revisión y borra el hash) la cambia, así que una lectura lenta que empezó antes de una edición no puede resucitar datos viejos — su publicación falla y se vuelve a leer, hasta 3 veces. Los escritores solo invalidan; nunca publican (regeneración perezosa), y son todos los que cambian algo de lo copiado: editar el producto, configurar o pausar la oferta, crear una reseña (cambia el resumen) y la reconciliación del inventario del administrador (cambia el precio normal; solo invalida las ofertas activas). Detalle en [README](../README.md) y en el encabezado de `ofertaDatosService.js`.
>
> **Sin cambios:** el checkout flash usa la consulta de stock para mostrar el producto y envía el precio esperado; la compra admitida sigue pasando por SQL; el reembolso Lua no recrea contadores vencidos; configurar una oferta activa conserva el reinicio explícito del cupo. El contador del cupo no es durable ante pérdida de Redis: SQL protege el inventario real, pero no reconstruye el cupo promocional. `npm run verificar:ofertaCache` (contra un Redis real, nueve escenarios) y `npm run test:redis` (30 pruebas aisladas) cubren el protocolo.

Segunda pieza de Entrega 2, el ítem de mayor peso de la rúbrica (3.0 pts) — plan completo en [ENTREGA-2-PLAN.md §4.2](ENTREGA-2-PLAN.md#42-oferta-de-inventario-limitado-implementado-y-verificado-2026-08-30).

- **Modelo:** `Producto.oferta_flash` (Mongo, embebido, 1:1 — mismo criterio que `resenas_resumen`): `{activo, precio_oferta, stock_oferta, vigente_desde, vigente_hasta}`. `stock_oferta` es el tamaño ORIGINAL del pool; el remanente en vivo vive únicamente en Redis. `activo` es un interruptor independiente de las fechas — permite pausar sin tocarlas, o preparar una oferta de antemano con `activo:false`. Comprar exige las dos cosas a la vez: `activo === true` Y estar dentro de `[vigente_desde, vigente_hasta]`.
- **Clave de Redis:** `oferta:{producto_id}:stock` — sin `ofertaId` separado, un producto tiene a lo sumo una oferta activa a la vez, así que `producto_id` alcanza. A diferencia del carrito, **sin TTL fijo**: el TTL se calcula como `segundos_hasta(vigente_hasta)` en el momento del lazy-init (primer intento de compra desde el último reinicio), así que la clave vence sola exactamente cuando termina la ventana anunciada — mismo mecanismo de vencimiento por TTL que el carrito, pero atado a una fecha en vez de a inactividad. Guardar la oferta desde el formulario de vendedor (`PATCH /api/ofertas/:id`) borra la clave si queda activa, para que el próximo intento la re-inicialice desde el `stock_oferta`/`vigente_hasta` (posiblemente nuevos) recién guardados.
- **Guardia 1 — admisión rápida en Redis:** un único script Lua (`config/redis.js`, registrado como `cliente.decrementarOferta(...)` vía `defineCommand`) que hace lazy-init (siembra + `EXPIRE`) y chequeo-y-decremento en una sola ejecución atómica — sin la ventana entre "leer" y "decrementar" que tendría un `DECR` simple más un chequeo separado en la aplicación. Devuelve el remanente o un sentinela de rechazo.
- **Guardia 2 — autoridad final en MySQL:** `checkoutService.checkoutOferta()`, función nueva y separada de `checkout()` (comparten el módulo, ninguna línea de código — "no reemplaza el checkout normal" también significaba no arriesgar el que ya está verificado). Valida pertenencia de dirección/método de pago igual que el checkout normal, exige stock REAL suficiente en `inventario` (puede rechazar aunque Redis ya haya admitido — es exactamente el caso que separa "admisión rápida" de "autoridad final"), cobra `precio_oferta` en vez de `inventario.precio`, y usa el campo `descuento` de `compra_detalle` (que en el checkout normal siempre queda en 0) para registrar el ahorro real.
- **Si la guardia 2 rechaza después de que la guardia 1 ya admitió** (stock real insuficiente, dirección/pago inválidos), `ofertaFlashService.comprar()` revierte el contador de Redis (`INCRBY`, mejor esfuerzo) — sin esto, un fallo del lado de MySQL quemaría igual una unidad del pool de oferta que nadie se llevó.
- **Compra directa, no por el carrito:** `POST /api/ofertas/:id/comprar` — siempre 1 producto, cantidad fija en 1 desde la UI (`OfertaCheckoutPage.jsx`, nueva, mismo layout de dirección/pago que `CheckoutPage.jsx` pero sin pasar por `CartContext.jsx`). `ProductDetailPage.jsx` consulta el remanente en vivo (`GET /api/ofertas/:id/stock`, pública) aparte de cargar el producto, y solo muestra el bloque de oferta si `activo && restante > 0`.
- **Verificación bajo concurrencia simulada** (requerimiento explícito del PRD): `npm run verificar:ofertaFlash` (`backend/scripts/verificarOfertaFlash.js`) siembra una oferta de 5 unidades sobre un producto real del seed y dispara 15 intentos de compra simultáneos (`Promise.allSettled`, contra `ofertaFlashService.comprar()` completo — las dos guardas, no solo Redis). Resultado real de la corrida: exactamente 5 admitidos, 10 rechazados con "No quedan unidades en oferta", contador final en Redis en exactamente 0, TTL de la clave > 0 tras terminar, e inventario REAL en MySQL descontado en exactamente 5 unidades — confirma que ninguna de las dos guardas sobrevendió ni dejó el contador en un estado inconsistente. Probado también a mano en el navegador de punta a punta: Luis configura la oferta desde `SellerProductFormPage.jsx` (con fechas convertidas correctamente entre UTC y hora local), el badge aparece en el detalle del producto con el precio tachado y el remanente, Ana compra una unidad desde `OfertaCheckoutPage.jsx` y el pedido queda confirmado al precio de oferta (referencia `TX-OFERTA-...`), con el remanente bajando de 3 a 2 tras la compra.

### 3.9 Entrega 2 — recomendaciones por tendencia (`tendenciaService.js`, `recomendacionRoutes.js`)

Agregada a pedido, complementaria a §3.8 (no la reemplaza) — plan completo en [ENTREGA-2-PLAN.md §4.5](ENTREGA-2-PLAN.md#45-recomendaciones-por-tendencia-implementado-y-verificado-2026-08-31).

- **De qué se trata:** en vez de que un vendedor configure a mano una oferta sobre su propio producto (§3.8), el sistema analiza el historial de compras de cada comprador y encuentra automáticamente productos similares de OTROS vendedores — mismos atributos (p. ej. Talla/Color, o Almacenamiento/RAM), sin que nadie lo active. Surgió de una pregunta real: "¿la oferta flash necesita Redis en esta forma?" — la respuesta fue que Redis pasa a cumplir dos roles distintos (caché del análisis + admisión atómica por usuario), no que deje de hacer falta.
- **Análisis** (`tendenciaService.analizarTendencia`): resuelve `compra_detalle` (MySQL) contra `Producto` (Mongo) en la aplicación, sin join real entre bases — encuentra la subcategoría con más unidades compradas, y dentro de ella, el valor más común POR NOMBRE de atributo (no un único par ganador) y el vendedor más comprado.
- **Coincidencias cruzadas** (`buscarCoincidencias`): productos activos de esa subcategoría de cualquier vendedor **menos el propio comprador** (desde 2026-10-04 nadie compra lo que vende, ver §3.7), puntuados por cuántos atributos preferidos comparten (no exige coincidencia total — un catálogo chico devolvería cero resultados si lo exigiera), con 15% de descuento sobre el precio normal.
- **Redis, dos roles:** `recomendaciones:{usuarioId}` cachea el resultado del análisis (TTL 1h, evita recalcular en cada vista del catálogo — rol nuevo, no existía en la oferta flash manual). `oferta-recomendada:{productoId}:{usuarioId}:stock` reutiliza el MISMO script Lua `decrementarOferta` de §3.8, sin cambios, pero con la clave por **(producto, usuario)** en vez de global — un cupo personal (2 unidades) en vez de un pool compartido entre todo el mundo, protege contra doble clic/reintento, no contra una carrera entre compradores distintos.
- **Guardia 2 reutilizada sin cambios:** `checkoutService.checkoutOferta()`, la misma función de §3.8. `tendenciaService.comprar()` vuelve a validar que el producto sea una recomendación vigente para ese usuario antes de comprar — nunca confía en un precio que mande el cliente, así nadie puede pedir el descuento en un producto cualquiera adivinando la URL.

### 3.10 Entrega 2 — panel de ventas con Cassandra

**Implementado; validación local registrada el 2026-09-05.** [ADR-004](ADR-004-analitica-ventas-cassandra.md) define el modelo; [ENTREGA-2-PLAN.md §4.6](ENTREGA-2-PLAN.md#46-panel-de-ventas-por-intervalos-y-ascenso-de-demanda-cassandra) mapea el alcance. Si se incluye hoy, su día puede seguir incompleto.
- **Límite de disponibilidad:** las métricas salen de Cassandra. Una caída se informa; no se sustituye por una consulta financiera a MySQL. La venta SQL puede confirmarse aun cuando su copia demore.
- **Operación:** `ventas:historico` carga o reconstruye el historial; `ventas:sincronizar` ejecuta una pasada y `test:ventas` comprueba reglas. Variables Cassandra y `VENTAS_SYNC_ENABLED`/`VENTAS_SYNC_INTERVAL_MS` documentadas en README.
- **Entorno:** Cassandra de un nodo para desarrollo, sin alta disponibilidad. Las ventas sintéticas conservadas por pruebas flash se incluyen como datos de ese entorno; no representan comercio real. Cancelaciones/reembolsos todavía requieren diseño de ajustes.

Consulta real de 30 días conciliada: cinco unidades, tres pedidos, Q68,069.80. HTTP devolvió 401 sin sesión, 403 para comprador y 200 para administrador. ### 3.12 Entrega 3 — búsqueda de productos con Elasticsearch

**Implementado y verificado, 2026-09-22.** Diseño completo en [PLAN-ELASTICSEARCH-BUSQUEDA.md](PLAN-ELASTICSEARCH-BUSQUEDA.md). Cierra el único requerimiento técnico de Entrega 3 que seguía sin empezar — la estrategia de consistencia (§3 de ese documento, ENTREGA-3-CONSISTENCIA.md) ya estaba lista desde el 2026-09-09.

- **Mapping deliberado** (requerimiento técnico explícito, no configuración por defecto): `descripcion`/`vendedor_nombre` como `text` con analizador `spanish` + subcampo `.keyword` (y, desde 2026-10-04, `vendedor_id` como `integer`, para saber si un resultado es del propio usuario — ver §3.7); `atributos` como `nested` (mismo motivo que `$elemMatch` en Mongo — sin eso, un filtro por nombre+valor podría cruzar el nombre de un atributo con el valor de OTRO atributo del mismo producto); `categoria`/`subcategoria` denormalizados como `keyword` para poder facetar (Elasticsearch no hace joins).
- **Tolerancia ortográfica** (requerimiento técnico): `fuzziness: 'AUTO'` en la consulta `multi_match` — probado con "camiceta" (typo real) encontrando "Camiseta premium de algodón orgánico" tanto en `verificar:busqueda` como en el navegador real.
- **Agregaciones reales** (requerimiento técnico): `terms` sobre categoría/subcategoría + agregación `nested` sobre atributos. Primera versión (2026-09-22) — desde 2026-10-20 las facetas son disyuntivas y traen árbol de categorías y precio, ver el último punto de esta sección.
- **Sincronización:** mejor esfuerzo, mismo criterio que Neo4j, no outbox durable como Cassandra — un resultado de búsqueda desactualizado por segundos no cuesta lo mismo que una venta perdida, y precio/stock reales siempre se releen de Mongo en detalle/carrito. Enganchada en `productoService.crear()`/`actualizar()`, reutilizando el mismo objeto que ya arma `obtener()` en vez de resolver subcategoría/categoría por su cuenta.
- **Integración en el frontend** (primera versión, 2026-09-22): `HomePage.jsx` usaba Elasticsearch solo cuando había texto de búsqueda (`q`); navegar por categoría sin texto seguía contra Mongo (`GET /api/productos`). Reemplazada el 2026-10-20: ahora la portada, las categorías y la búsqueda son una sola consulta a `GET /api/busqueda` (último punto de esta sección).
- **Dos bugs preexistentes reales, encontrados al construir esto (no introducidos hoy):** `productoService.js` `formatear()` nunca incluía `total_vendido` en el objeto que devuelve, aunque `listar()` ya lo usaba para ordenar — nadie lo notó porque nada lo leía todavía; el nuevo sort "más vendidos" de la búsqueda sí lo necesitaba, así que se agregó. Y un script aislado que llama `productoService.listar()` (con su `populate` hasta `Categoria`) falla con "Schema hasn't been registered for model Categoria" si nada en su propio árbol de `require` registró ese modelo antes — mismo tipo de gotcha ya documentado para otros scripts aislados en este proyecto, corregido en `backfillBusqueda.js` con un `require` explícito solo por el efecto de registro.
- **Verificación:** `npm run busqueda:backfill` indexó el catálogo real (106 productos: el seed original más 100 agregados el 2026-09-22 con `scripts/sembrarCatalogo.js`, 12 subcategorías nuevas, idempotente). `npm run verificar:busqueda` pasa cuatro pruebas contra datos reales (no sintéticos): tolerancia ortográfica, relevancia real ("camiseta premium" rankea la que coincide en las dos palabras antes que la que coincide en una), agregación real (facetas de la subcategoría Camisetas — aserción por inclusión, `>= 2` resultados con Talla:M y Color:Azul presentes, no un conteo exacto congelado, para no quedar obsoleta cada vez que crece el catálogo), y autocompletado (ver abajo). Confirmado también en navegador real.
- **Autocompletado (agregado 2026-09-22, después de que la tolerancia ortográfica ya estaba verificada):** `completion` suggester dedicado (no reutiliza el `multi_match` de la búsqueda de texto) sobre un campo nuevo `sugerencia`, con `contexts` por `estado` para que un producto inactivo (se indexa igual que uno activo) nunca aparezca como sugerencia — sin eso, la sugerencia llevaría a una búsqueda con cero resultados. `conectar()` ahora aplica `putMapping()` también sobre un índice ya existente (antes solo al crearlo), así que este campo nuevo se sumó sin recrear el índice de 106 productos ya indexado. `GET /api/busqueda/sugerencias?q=`, endpoint público. UI en el buscador ya existente del header (`Header.jsx`): dropdown con debounce de 250ms, navegación por teclado, clic-afuera-cierra. Un bug real encontrado probando en navegador (el dropdown se reabría solo después de seleccionar una sugerencia, mostrando sugerencias sobre la propia página de resultados) se corrigió antes de darlo por terminado. Detalle completo en PLAN-ELASTICSEARCH-BUSQUEDA.md §12.
- **Una sola consulta para buscar y navegar, con facetas disyuntivas (2026-10-20):** `categoria_id`, `subcategoria_id` y `atributos` ya existían como `keyword`/`nested` en el índice, pero la portada seguía leyendo Mongo para navegar y calculaba las facetas en el navegador, y las del motor se encogían al marcar un valor (marcar `Talla=M` escondía `S`, `L` y `XL`). Ahora `GET /api/busqueda` sirve la portada, las categorías y la búsqueda de texto: sin `q` es un `match_all`; categoría, precio y atributos van en un `post_filter` y cada agregación aplica todos los filtros menos el suyo, así que el árbol de categorías (con conteos y migas de pan), los atributos (con selección múltiple: M o L; Talla M y Color Azul) y las cubetas de precio nunca colapsan a lo elegido. Además orden (más vendidos, precio ↑/↓), paginación (60 por página) y todo en la URL (el botón «atrás» funciona). Los dos caminos —el motor y, con Elasticsearch apagado, el respaldo en Mongo— comparten un módulo puro (`facetasBusqueda.js`), así que la respuesta tiene la misma forma. Se corrigió de paso un hueco real: `?incluirInactivos=1` por la URL pública devolvía productos dados de baja (ahora esas opciones son internas), y `categoriasDelIndice` contaba también los inactivos. **Verificado:** 241 pruebas unitarias de las suites del backend sin fallas (`test:busqueda` 49, `test:resiliencia` 57, las demás sin cambios), `verificar:busqueda` con 11 pruebas contra el catálogo real (incluida la paridad motor/Mongo en 11 de 11 combinaciones), la API contra los contenedores apagados de verdad (sin Elasticsearch 17 de 17 respuestas en modo básico, 16 idénticas a las del motor; sin Mongo 17 de 17 desde el índice) y el navegador real, de escritorio y de celular. Límites: el orden «más vendidos» sale del `total_vendido` indexado; los atributos solo se ofrecen con una subcategoría a la vista. Detalle en PLAN-ELASTICSEARCH-BUSQUEDA.md §15.
- **Sugerencias cuando un texto no encuentra nada (2026-10-21/22, Jose; revisión y correcciones 2026-10-23):** el mismo `GET /api/busqueda` acepta ahora una sesión *opcional* (`optionalAuth`: un token inválido o una cuenta suspendida se tratan como anónimo) y, si un texto no da resultados, suma `sugeridos` con la última actividad del usuario (búsqueda que sí funcionó o último producto activo visto, guardados en Redis `actividad:{id}`, 5 entradas, 30 días), su historial de compras o los más vendidos. No es similitud semántica. La revisión encontró y corrigió un 503 con `?q` repetido, un producto pausado sugerido como «lo último que viste» y el stock viejo en las sugerencias, y dejó `test:resiliencia` otra vez en verde (70 pruebas). Detalle en PLAN-ELASTICSEARCH-BUSQUEDA.md §16.

### 3.13 Entrega 3 — degradación elegante con una o varias bases apagadas

**Implementado y verificado en vivo, 2026-10-19/20.** El requerimiento se comprueba apagando el contenedor de una o de varias bases con la aplicación corriendo: tiene que seguir siendo utilizable, sin los datos de esa base. Medición completa (antes/después de las seis bases, combinaciones, riesgos aceptados) en [ENTREGA-3-CONSISTENCIA.md](ENTREGA-3-CONSISTENCIA.md) §7.

- **Qué se encontró:** no lo cumplía. Con Redis apagado hasta el catálogo público tardaba ~108 s por petición y el carrito y el checkout no respondían; con Neo4j una compra tardaba 31 s; con MySQL el login devolvía `401` con la ruta de un archivo de Prisma y la interfaz cerraba la sesión. El código ya fallaba abierto casi en todos lados: lo que faltaba era **fallar rápido**.
- **Cómo se resolvió:** tiempos acotados en cada cliente (`config/redis.js`, `mongo.js`, `prisma.js`, `neo4j.js`, `cassandra.js`, `elasticsearch.js`), un cortacircuitos mínimo y un error tipado `503 SERVICIO_NO_DISPONIBLE` (`utils/resiliencia.js`, `utils/http.js`), y **respaldos cruzados**: con Mongo apagado el catálogo, el detalle, las categorías y el estado de publicación que exigen el carrito y el checkout salen del índice de búsqueda (`catalogoLecturaService.js`, `productoService.estadoPublicacion`); con Elasticsearch apagado la búsqueda cae a Mongo. Lo que Mongo no pudo recibir se repara solo al volver (`reconciliacionMongoService.js`).
- **Que se vea:** `GET /api/health/componentes` (qué base responde: `completo`/`degradado`/`critico`; público y sin detalle interno, y con el token de un administrador suma milisegundos y texto del error), una franja en el frontend (`AvisoServicios.jsx`) que dice qué cambia, y la sesión ya no se cierra con un `503` (`AuthContext.jsx`).
- **Resultado:** con cualquiera de las seis apagadas —o con Redis, Elasticsearch, Neo4j y Cassandra apagadas a la vez— el comprador navega, busca, entra, arma el carrito y **completa una compra en ~1 s**; solo se pierde lo que depende de esa base (paneles de ventas y fraude, ofertas flash, edición del catálogo, cuentas y pedidos si es MySQL). Con las seis apagadas el backend arranca igual y todo vuelve solo, sin reiniciarlo.
- **Verificación:** `npm run test:resiliencia` (49 pruebas) + las suites existentes (190 en total) + la medición con contenedores reales. Cómo probarlo a mano: `docker stop tiendaya-redis` (o varios) y `curl http://localhost:3000/api/health/componentes`.

### 3.14 Entrega Final — control de acceso (API, Redis y MongoDB)

**Implementado y verificado, 2026-10-23.** Ítem «Control de acceso» de [PLAN-ENTREGA-FINAL.md](PLAN-ENTREGA-FINAL.md) §4; diseño y evidencia en [ADR-007](ADR-007-control-de-acceso.md), uso en el README («Control de acceso»). Primero se corrigieron cuatro huecos de la API; Una revisión de `routes/*` y `services/*` contra el OWASP API Top 10 encontró cuatro endpoints que mostraban de más; se corrigieron antes de poner cuentas de servicio en las bases porque es lo más barato y lo más fácil de demostrar («encontré un bug y veo de más»).

- **Historial de un producto** (`GET /api/productos/:id/historial`, BOLA): exigía rol de vendedor pero no que el producto fuera suyo, así que cualquier vendedor leía precios y stock históricos de otro. Ahora `verificarPermiso` (dueño o administrador; MySQL decide quién es el dueño, igual que al editar) y otro vendedor recibe `403`. Un id que no es un entero positivo da `404` sin llegar a MySQL. La pantalla de detalle solo ofrece el historial al dueño y al administrador.
- **Reseñas públicas** (`GET /api/productos/:id/resenas`): devolvían `usuario_id` y el nombre completo del autor. Ahora sale un alias («Ana G.») y ningún id de cuenta, para cualquier rol (`resenaService.alias`).
- **Estadísticas de ediciones** (`GET /api/productos/estadisticas/ediciones`): no pedía sesión. Ahora solo el administrador; el panel administrativo manda su token.
- **Salud** (`GET /api/health/componentes`, `routes/saludRoutes.js`): el campo `error` traía el texto del driver (hasta 160 caracteres: host, puerto, usuario). Ahora el público solo ve `ok` por base y el detalle completo exige token de administrador.
- **Lista blanca de la API:** `src/config/politicaRutas.js` declara las 53 rutas del backend con su acceso. `tests/accesoRutas.test.js` carga el `app.js` real y falla si una ruta no está declarada, si una declarada ya no existe o si el acceso real no es el declarado; y prueba por HTTP, en cada ruta protegida, el 401 sin sesión y el 403 de cada rol que no figura en su lista. Una ruta nueva sin declarar ya no pasa la suite.
- **Redis:** el usuario `default` está apagado y cada módulo del backend entra con su cuenta (`rd_carrito`, `rd_candados_r`/`rd_candados_w`, `rd_ofertas`, `rd_cupos`, `rd_recomendaciones`, `rd_actividad`, `rd_salud`, y `rd_admin` solo para scripts), con solo los comandos y las llaves de ese módulo (`src/config/redisCuentas.js`). `config/redis.js` abre un cliente por cuenta; `npm run seguridad:inicializar` genera las contraseñas (en `backend/.env`) y `docker/redis/users.acl` (solo hashes).
- **MongoDB:** autenticación activada con `--keyFile`. El servidor web entra como `mg_app` (rol `app_tiendaya`): lee, inserta y actualiza el catálogo y las reseñas, no borra nada, y del historial de cambios (`producto_eventos`) **solo lee e inserta**, de modo que un evento no se puede modificar ni borrar ni con un bug. `npm run seguridad:mongo` crea el rol y los usuarios. Probado con una copia de los datos reales, con un volumen nuevo y en el contenedor real.
- **Un rechazo de credenciales no es una caída:** `500 CREDENCIAL_RECHAZADA` sin detalle para el cliente, una línea en el log por cuenta, cerrojo que corta el bucle de reintentos y se reabre a los 30 s, y fallo **cerrado** de la suspensión, los límites suaves, el tope de pedidos por hora y los intentos de contraseña. Probado con fallas provocadas en vivo.
- **Puertos:** Redis y MongoDB se publican solo en `127.0.0.1`.
- **Verificación:** `npm run test:acceso` (lista blanca de rutas, cuentas de Redis y Mongo, errores de credencial y los 14 casos de los huecos de la API), con las protecciones comprobadas **deshaciéndolas** (62 mutaciones, todas detectadas); `npm run verificar:acceso` contra los contenedores reales (88 comprobaciones, 0 fallas; en Redis lo negado se ejecuta y queda en `ACL LOG`); los flujos reales con `ACL LOG` vacío; y toda la suite del backend en verde. Quedan como decisiones aparte las categorías abiertas a cualquier vendedor y el límite de intentos de login (plan §4.1, filas 5 y 6).
- **Decisión asociada (plan §3.4b):** los vectores de la búsqueda semántica vivirán **solo en Elasticsearch**, sin copia en Mongo. Se comprobó contra el Elasticsearch real y quedan tres reglas: nunca reindexar un producto sin recalcular su vector, excluir `embedding` de `_source` en las demás consultas, y tratar el modelo como parte de la preparación de la demo.

### 3.15 Entrega Final — recomendación semántica (vectores en Elasticsearch)

**Implementado y verificado, 2026-10-25.** Ítem «Recomendación semántica» de [PLAN-ENTREGA-FINAL.md](PLAN-ENTREGA-FINAL.md) §3; diseño, alternativas medidas, evidencia y límites en [ADR-006](ADR-006-recomendacion-semantica-vectorial.md), uso en el README («Productos relacionados por significado»).

- **Modelo local:** `multilingual-e5-small` (ONNX cuantizado, MIT, 384 dimensiones) con `@huggingface/transformers` dentro del backend: sin internet ni claves. Vive en `backend/modelos/` (fuera de git); `npm run modelo:descargar` lo baja con revisión fija y comprueba tamaño y SHA-256, `npm run modelo:verificar` solo comprueba. Windows + ONNX funciona: carga ≈ 0,9 s, ≈ 500 MB residentes, 2,5–3,8 ms por título.
- **Vectores solo en Elasticsearch** (campo `embedding`, `dense_vector` coseno `int8_hnsw`), sin copia en Mongo. `indexarProducto` los recalcula en cada alta o edición; si el modelo falta hace un `update` parcial que **conserva** el vector (un `index` completo lo borraría: comprobado), y toda otra consulta excluye `embedding` de `_source`. `npm run busqueda:backfill` recalcula los 121 productos en 5 s y se detiene si falta el modelo.
- **`GET /api/productos/:id/relacionados`** (pública, sesión opcional, en la lista blanca): kNN con los filtros dentro de la búsqueda (solo activos, sin el propio producto, sin vendedores suspendidos, sin lo del propio vendedor), umbral de coseno 0,90, lo agotado al final con el stock de Mongo, sin repetidos y a lo sumo la mitad de la lista del mismo vendedor. Capas: por significado → misma subcategoría (Mongo) → nada; con Mongo apagado sigue por significado, con Elasticsearch apagado cae a la subcategoría y con ambos apagados responde 503.
- **Interfaz:** sección «Productos relacionados» en la ficha del producto (`ProductosRelacionados.jsx`) con una leyenda del modo («Parecidos a …» / «Misma subcategoría: …») y el aviso global de servicios actualizado.
- **Resultados** (`npm run verificar:similares`, 106 productos reales): precisión@5 **91,2 %** frente a 71,1 % de BM25; 15 productos sin ningún vecino con BM25 y ninguno sin sección con vectores; consultas coloquiales: el buscador por texto resuelve 0 de 14 y los vectores 6 de 14 (la jerga regional queda para los sinónimos). Limitación declarada: la etiqueta es la subcategoría y el texto incrustado ya la incluye (solo con el título: 64,7 %).
- **Verificación:** `npm run test:similares` (66 pruebas: reglas, forma de las consultas, cadena de capas, contrato del modelo e indexado sin pisar el vector) + 2 del mapping; la suite del backend (401) en verde; 51 de 52 mutaciones deliberadas detectadas (la restante es equivalente); en vivo, con los contenedores detenidos y vueltos a iniciar.

### 3.16 Entrega Final — pantalla de permisos (`/admin/permisos`)

**Implementada y verificada, 2026-10-25.** Extra del ítem de control de acceso ([§3.14](#314-entrega-final--control-de-acceso-api-redis-y-mongodb)); diseño, referencias reales y límites en [ADR-007 §9](ADR-007-control-de-acceso.md), uso en el README.

- **Qué es:** un administrador ve y ajusta qué roles usan 13 acciones del panel (ventas, fraude, suspensiones, mantenimiento, estadísticas, crear categorías), crea roles propios, asigna roles a las cuentas, prueba una decisión en un simulador y revisa quién cambió qué. Mejor esfuerzo: con Mongo apagado el cambio se aplica igual y la respuesta dice `auditado: false`.
- **Interfaz:** cuatro pestañas (matriz, simulador, cuentas y roles, auditoría), `/api/auth/me` devuelve los permisos de la cuenta y el frontend los usa (`RequirePermiso`, menú, panel); sin errores en la consola ni desborde a 375 px.

La prueba de la lista blanca encontró un error real en su primera corrida (la clave de `router.post('/')` salía con una barra de más).

## 4. Problemas reales encontrados y resueltos

Esta lista importa porque casi todos se descubrieron construyendo (no leyendo el diagrama), y cada uno se corrigió en el momento en vez de quedar como deuda:

- **Faltaba la entidad `pago`** — el modelo original no separaba "instrumento guardado" de "cobro real". Agregada.
- **CVV y número de tarjeta en `decimal`** — corregido a token de pasarela + últimos 4 dígitos (nunca se guarda el número completo ni el CVV).
- **`atributo_producto` sin campo `valor`** — no se podía registrar, por ejemplo, que el color de un producto es "Rojo". Agregado.
- **`producto` sin dueño** — cualquier `vendedor` podía editar el catálogo de cualquier otro. Se agregó `id_vendedor` con permisos aplicados (y migración con backfill sobre los datos ya existentes).
- **`compra_detalle` sin `cantidad`** — se guardaba el total de la línea pero no las unidades compradas; el historial de pedidos no podía mostrar "2 × Camiseta". Agregado (detectado recién al construir esa pantalla).
- **Auto-registro con rol elegible por el cliente** — permitía autoasignarse `administrador`. Corregido: el registro siempre fuerza `comprador`.
- **Checkout sin validar dueño de dirección/método de pago** — un usuario autenticado podía usar la dirección o tarjeta de otro (IDOR). Corregido.
- **Checkout sin validar cantidades positivas** — una cantidad negativa pasaba la validación de stock y *aumentaba* el inventario en vez de restarlo. Corregido.
- **`token_pasarela` se devolvía en el listado de métodos de pago** — sin necesidad, ya que el cliente nunca debería volver a leerlo. Ocultado.
- **Buscador del frontend sin soporte en el backend** — se construyó la barra de búsqueda antes de que `GET /api/productos` supiera filtrar por texto. Se agregó un filtro simple (no es el buscador de texto libre con tolerancia ortográfica que pide el PRD para Entrega 3 — eso sigue pendiente).
- **Permisos de la shadow database de Prisma (3 rondas)** — cada migración nueva exponía un permiso que faltaba (crear/borrar la base, después `ALTER`, después `UPDATE` para un backfill). Se resolvió con un único grant bien acotado en vez de seguir ampliando permisos globales uno por uno. Detalle en [ADR-001](ADR-001-stack-y-migraciones.md#notas-de-implementación-2026-08-22).
- **CLI de Prisma no interactivo bloqueando migraciones "riesgosas"** — pasó dos veces (backfill de `id_vendedor`, restricción unique de `atributo_producto`), incluso ya habiendo verificado que el cambio era seguro. Sin flag para forzarlo; la solución fue escribir la migración a mano y aplicarla con `prisma migrate deploy`.
- **La migración a Mongo, tal como estaba diseñada originalmente, iba a romper la atomicidad del checkout** — mover `precio`/`cantidad` a Mongo (como decía la primera versión de ADR-002) hubiera dejado el descuento de inventario y la creación del pedido en dos bases distintas sin transacción conjunta. Se detectó al planificar la implementación, antes de escribir código, y se resolvió con el modelo dividido (§3.2 de ADR-002): precio/cantidad se quedan en MySQL, checkout no se toca.
- **Las transacciones multi-documento de Mongo necesitan un replica set**, incluso de un solo nodo — un `mongod` standalone no las soporta. Configurado en `docker-compose.yml` con auto-inicialización vía healthcheck.
- **Un MongoDB nativo de Windows, instalado fuera de este proyecto, competía por el puerto 27017** con el contenedor de Docker — Compass, `mongosh` y cualquier cliente conectando a `localhost:27017` hablaban con el Mongo equivocado (vacío), silenciosamente. Se diagnosticó mal al principio (se pensó que era algo específico de PowerShell) hasta que se revisó el puerto en detalle. Corregido moviendo el contenedor al puerto 27018, adentro y afuera. Detalle completo, incluyendo el diagnóstico incorrecto inicial, en [ADR-002 §8](ADR-002-migracion-catalogo-documental.md#8-notas-de-implementación-2026-08-23).
- **Auditoría de qué funciones del backend no tenían consumo real en el frontend** — comparar cada `api/*.js` contra dónde se llama (con cuidado: varias llamadas están encadenadas en varias líneas, tipo `productosApi\n.obtener(id)`, así que un grep ingenuo de una sola línea da falsos negativos) encontró tres funciones construidas pero nunca usadas desde la UI: `direccionesApi.eliminar` y `metodosPagoApi.eliminar` (el backend soporta borrar, no hay botón que lo llame en ningún lado) y el historial de cambios, que sí tenía UI ahora (ver arriba) pero no la tenía hasta esta sesión. Ver [ESTADO-PROYECTO §5](#5-limitaciones-conocidas-decisiones-explícitas-no-descuidos) para lo que sigue pendiente.
- **Borrar una dirección o método de pago ya usado en un pedido tiraba un error de Prisma crudo** (violación de foreign key — `compra.id_direccion`/`pago.id_metodo_pago` no tienen `onDelete` configurado, por lo que MySQL rechaza el borrado por diseño, no por bug), envuelto además en un `404` que no correspondía. El mensaje incluía rutas de archivo del servidor — un detalle de información de más para un error de cliente. Se encontró al construir la UI de borrado en `/cuenta` (Ana, la usuaria de prueba, ya tenía pedidos con su única dirección/tarjeta). Corregido: `direccionService.js`/`metodoPagoService.js` capturan el código `P2003` de Prisma y devuelven un `409` con "tiene pedidos/pagos asociados" — el comportamiento correcto es que no se pueda borrar, no que el error confunda.
- **`scripts/verificarCheckout.js` se quedaba colgado indefinidamente** (nunca terminaba el proceso, aunque el checkout ya había corrido bien y el script había impreso su resultado) después de agregar la actualización de `total_vendido` (ver §3.3): ese paso nuevo abre una conexión de Mongoose desde `checkoutService.js`, y el script solo desconectaba Prisma en su `finally`, nunca Mongoose — la conexión abierta mantenía vivo el proceso de Node aunque `main()` ya hubiera terminado. Corregido agregando `mongoose.disconnect()` al `finally` del script. Se detectó porque el comando corrió más de 120s sin motivo aparente (`verificar:checkout` normalmente tarda menos de un segundo) — señal de que algo estaba impidiendo que el proceso saliera, no de que el checkout en sí fuera lento.
- **El pool de conexiones de Prisma queda atascado si el contenedor de MySQL se recrea mientras el backend sigue corriendo** (`pool timeout: failed to retrieve a connection from pool`, `active=0 idle=0` — ni ocupado ni libre, simplemente no logra abrir una conexión nueva). Pasó dos veces en esta sesión, la segunda con un matiz importante: **un solo reinicio del backend no siempre alcanza**. Si el `node src/server.js` nuevo arranca y hace su primera consulta *mientras* MySQL todavía está terminando de recuperarse tras el recreate (aunque `docker ps` ya lo muestre `healthy`), ese primer intento de conexión del adaptador puede fallar y dejar el pool en un estado atascado que no se autorepara — un segundo reinicio, ya con MySQL estable, sí lo resuelve. Diagnóstico que lo confirmó: MySQL sano (`Threads_connected` bajo, `SELECT 1` instantáneo por CLI), una conexión TCP cruda de Node a `localhost:3306` exitosa en ~20ms, el driver `mariadb` crudo conectando bien, y un `PrismaClient`+adaptador armado en un script aislado (mismo patrón que `config/prisma.js`) conectando bien — descartando red, el driver y el código, dejando como única variable el *momento* en que el proceso en vivo abrió su pool. Lección práctica: si reiniciar el backend una vez no alcanza después de un `docker compose up/restart`, probar reiniciarlo una segunda vez antes de sospechar de un bug de código.
  - **Resuelto de raíz (2026-08-29):** se encontró la causa real detrás de esta intermitencia. Un script aislado que armaba su propio `PrismaClient`+adaptador (mismo patrón que arriba) reveló el error completo, que el mensaje de "pool timeout" normalmente tapa: `RSA public key is not available client side`. El usuario `tiendaya` de MySQL usa `caching_sha2_password` (el default de MySQL 8.4) — sin `allowPublicKeyRetrieval=true` en la cadena de conexión, la *primera* conexión de un pool nuevo sin TLS puede fallar pidiendo la clave RSA del servidor, y esa falla se manifiesta río arriba como "pool timeout (active=0 idle=0)" sin ningún detalle de la causa real. Agregado `?allowPublicKeyRetrieval=true` a `DATABASE_URL` en `backend/.env` (y a `backend/.env.example`, que sí está versionado — `.env` no lo está). Confirmado con el mismo script aislado (fallaba sin el parámetro, conectaba al instante con él) y con un reinicio real del backend, que arrancó limpio a la primera. Es un candidato muy fuerte para haber sido la causa real de **todos** los "pool timeout" intermitentes de esta sesión, no solo del último — pero no se puede afirmar con certeza total sin haber reproducido cada incidente anterior con este diagnóstico puesto.
- **`SellerProductFormPage` podía dejar un atributo del producto invisible e inaccesible en el formulario de edición.** Los campos editables de la sección "Atributos" salían solo de `subcategoriaActual.atributos_categoria` (la plantilla vigente de la subcategoría), no de los atributos que el producto realmente tenía guardados. Si un producto tenía un atributo cuyo nombre ya no estaba en esa plantilla (plantilla editada después de crear el producto, u otro desajuste de datos), ese atributo no aparecía como campo editable — la única opción visible era "+ Crear nueva", que además fallaba con un error si el nombre ya existía en `atributos_definidos`. Reportado por el usuario como "no puedo modificar la talla, solo puedo agregar un atributo nuevo"; no se pudo reproducir tal cual con el producto de prueba (Camiseta #1, Talla/Color sí estaban en la plantilla y editarlos funcionó de punta a punta), pero la causa raíz identificada aplica en general. Corregido en `SellerProductFormPage.jsx` calculando `atributosDisponibles` como la unión entre la plantilla de la subcategoría y las claves ya presentes en `valoresAtributos` (los atributos cargados del producto), no solo la plantilla — así ningún atributo existente queda oculto, sin importar si sigue en la plantilla actual. Un solo componente compartido entre `/vendedor/productos/:id/editar` y `/admin/productos/:id/editar`, así que la corrección cubre ambos roles.
- **`productoService.crear()` quedó roto por la limpieza de columnas del 2026-08-30** (ver arriba) — seguía armando `prisma.producto.create({data: {descripcion, imagen_url, estado, ...}})`, y esas tres columnas ya no existían en MySQL. Nadie lo notó en el momento porque toda la verificación posterior a esa limpieza editó productos existentes, nunca creó uno nuevo. Encontrado al probar crear un producto después de anidar `precio`/`cantidad` en Mongo (ver punto de arriba) — error de Prisma claro (`Unknown argument 'descripcion'`), no un fallo silencioso. Corregido quitando esas tres claves del `data` (la fila de `producto` en MySQL solo necesita `id_vendedor` + `inventario` anidado).
- **Un producto `estado: "inactivo"` seguía apareciendo en el catálogo público** (`GET /api/productos`, `HomePage.jsx`) — encontrado al dejar `inactivo` un producto de prueba y verlo listado igual, con badge de stock normal. `productoService.listar()` nunca filtró por `estado`. **Corregido (2026-08-30):** `listar()` ahora excluye `inactivo` por defecto. La parte no trivial fue decidir *quién* puede pedir ver los inactivos igual — un vendedor necesita seguir viendo (y pudiendo reactivar) sus propios productos inactivos en `/vendedor`, y un administrador necesita verlos todos en `/admin`, así que "público" no podía significar simplemente "sin filtro". Se agregó `optionalAuth` (`middleware/auth.js`) — como `requireAuth` pero no rechaza si no hay token — a `GET /api/productos`; la ruta calcula `mostrarInactivos` a partir de `req.usuario` (nunca de un query param): `true` si es `administrador`, o si es `vendedor` y el `vendedorId` pedido coincide con su propio `id_usuario` del token. Un vendedor pidiendo `?vendedorId=` de otro no obtiene los inactivos ajenos — se verificó explícitamente con el token de un segundo vendedor de prueba. El frontend (`SellerDashboardPage.jsx`, `AdminDashboardPage.jsx`) ahora manda su token en `productosApi.listar()`; `HomePage.jsx` sigue sin mandarlo, que es lo que lo mantiene filtrado a solo activos.
- **La caché de la oferta flash guardaba solo una parte del producto y su TTL fijo de 60 s no seguía la regla del carrito (2026-10-03, rediseñada el 2026-10-04).** Se detectó porque se comprobó en Redis que el carrito y la oferta no tenían todos los datos del producto; además, cada editor "publicaba" los datos en vez de solo invalidarlos, una regla distinta de la del carrito. Se rehízo con el protocolo del carrito (hash con formato, revisión, lectura y publicación atómicas en Lua; ver §3.8). Al revisarlo se encontró además un hueco propio: **dos escritores cambiaban algo que la copia incluye sin invalidarla** — una reseña nueva (el resumen de reseñas) y la reconciliación del inventario del administrador (el precio normal) —, de modo que una oferta muy consultada, con TTL deslizante, habría mostrado ese dato viejo hasta su fin. Ambos invalidan ahora, con una prueba aislada y un escenario contra Redis real (`verificar:ofertaCache`, el 9). Al escribirlo apareció el mismo problema por otro lado: como cada lectura renueva el TTL, **una invalidación perdida** (Redis inalcanzable justo al editar) mantendría la copia vieja mientras alguien la leyera — y el precio de oferta que se cobra sale de ella. Se añadió una **edad máxima de 600 s** (la señal d de regeneración): pasado ese tiempo la lectura descarta la copia aunque siga viva, con una prueba aislada y un caso en `verificar:ofertaCache`.
- **Renombrar un producto dejaba nodos `Articulo` huérfanos en el grafo (2026-10-04, al construir §19).** Al probar el cambio de título, el artículo de la descripción anterior se quedaba en Neo4j sin ningún producto enlazado. Corregido en la misma consulta compartida (`MERGE_PRODUCTO_Y_VENDEDOR`: una subconsulta unitaria desenlaza el producto del artículo anterior y borra el que se quede sin productos; `fraude:backfill` también limpia los huérfanos) y cubierto por `verificar:fraude` (cambiar el título hace desaparecer el hallazgo; volver a ponerlo lo trae de vuelta; todo `Producto` del grafo tiene exactamente un `ES_ARTICULO`).
- **El cliente de Prisma generado en `node_modules` queda obsoleto tras traer migraciones de otra persona (2026-10-04)**: los scripts fallaban con `Unknown argument id_usuario_id_producto` aunque la migración ya estuviera en el repositorio. Hace falta `npm run prisma:deploy` y `npm run prisma:generate`, y **reiniciar el backend** (nodemon no recarga el cliente de `node_modules`). Mismo tipo de trampa que el pool de conexiones de arriba: el síntoma está lejos de la causa.
- **Las pruebas aisladas cargan cada servicio con dobles de sus dependencias, y un `require` nuevo sin su doble arrastra el módulo real** (2026-10-04): al añadir la regla de producto propio y el compromiso de no reventa, 13 pruebas de `test:redis` y 4 de `test:ventas` fallaron porque el servicio cargaba Prisma de verdad. Cada dependencia nueva de un servicio con pruebas aisladas necesita su doble en `tests/redisHelpers.js` (`productoFalso`, `compromisoFalso`) o en el cargador de la prueba.
- **Los procesos de `npm run dev` (backend y frontend) murieron varias veces sin error visible** al implementar el carrito — el log mostraba el arranque exitoso (`escuchando en http://localhost:3000`, Vite `ready`) y el puerto llegaba a estar `LISTENING`, pero el proceso desaparecía poco después, sin stack trace ni mensaje de `nodemon` de crash. No se llegó a una causa raíz tan clara como la de `allowPublicKeyRetrieval` (ver más abajo) — el patrón que terminó siendo confiable fue lanzar con `nohup ... & disown` (no solo `nohup ... &`) y verificar el puerto con un chequeo real (`netstat`/`curl`) después de dejar pasar tiempo genuino entre pasos, no inmediatamente después de arrancar. Anotado por si vuelve a pasar — no se pudo confirmar si fue un problema del entorno (Git Bash sobre Windows) o de la forma en que se estaban encadenando comandos en la misma sesión.
- **Reseñas (`Resena.js`/`resenaService.js`, 2026-09-08) se podían crear sin haber comprado el producto, y sin límite de una por usuario.** El endpoint requería sesión pero no rol comprador ni compra real — cualquier cuenta (sin fricción, el registro público es gratis) podía dejar cualquier cantidad de reseñas en cualquier producto, habilitando inflar o hundir una calificación con cuentas creadas solo para eso. Corregido: `crear()` exige una compra con pago aprobado del mismo producto (misma definición de "compra real" que ya usa `ventasSyncService.js`/ADR-004 para el panel de ventas — un solo criterio, no dos que se puedan desalinear) y un índice único `{producto_id, usuario_id}` en Mongo (la garantía real bajo concurrencia; el chequeo previo en la aplicación es solo para devolver un 409 legible en el caso normal). Verificado con los tres casos: sin compra → 403, con compra real → creada, repetir → 409.
- **Puerto 6379 (Redis) no lograba bindear en Windows** con un error de permisos (`forbidden by its access permissions`), no de "puerto ocupado" — confirmado con `netsh int ipv4 show excludedportrange protocol=tcp` que ese puerto cae dentro de un rango que Hyper-V/WSL2 reserva en esta máquina. Corregido parametrizando el puerto del host en `docker-compose.yml` (`${REDIS_HOST_PORT:-6379}`, sin cambiar el comportamiento por defecto para quien no tenga este problema) y un `REDIS_HOST_PORT=16379` en un `.env` de la raíz (no versionado).
- **`Direccion`/`MetodoPago` en Neo4j clavados por el id de MySQL, encontrado como error propio al verificar** — cada fila de `direcciones`/`metodo_pago` pertenece a un solo usuario, así que dos cuentas nunca podrían compartir ese id por construcción; la señal de "dirección compartida entre cuentas" jamás habría encontrado nada, sin importar los datos. Corregido antes de terminar la implementación (no llegó a quedar sin detectar) — ver PLAN-NEO4J-DETECCION-FRAUDE.md §12. (Modelo reemplazado el 2026-10-04: `Direccion`/`MetodoPago` ya no existen; la identidad entre cuentas pasó a ser el nombre completo normalizado y el buzón de correo normalizado — claves que sí pueden repetirse entre cuentas; el `usuarios.correo` exacto, en cambio, es único y nunca lo haría, por eso se compara el buzón tras quitar alias y puntos de Gmail — ver §16, §17 y §18.)
- **Varios scripts de un solo uso, corridos directo con `node -e "..."` durante esta sesión, se quedaron colgados indefinidamente por no llamar `neo4j.cerrar()`/desconectar el driver al final** — un proceso Node con una conexión de Neo4j abierta no sale solo. Además, herramientas de shell reportaron un PID que no correspondía al proceso real de Windows (`taskkill //PID <N>` devolvía "no encontrado" para un proceso que sí estaba vivo) — confirmado con `Get-Process`/`Stop-Process` de PowerShell, que sí ven el PID real. Lección: para procesos que puedan quedar colgados, cerrar explícitamente cada conexión (`prisma.$disconnect()`, `mongoose.disconnect()`, `redis.disconnect()`, `neo4j.cerrar()`) en un `finally`, y verificar/matar procesos con PowerShell si Bash reporta un PID que no coincide con lo esperado.

## 5. Limitaciones conocidas (decisiones explícitas, no descuidos)

- **La caché del carrito expira en Redis** tras 450s de inactividad; se recupera desde SQL/Mongo. Leerlo caliente usa solo Redis: su copia puede quedar desactualizada hasta revisar el checkout, una mutación o una carga fría. No reserva inventario; precio/stock se validan al confirmar. Los datos de la oferta flash siguen el mismo protocolo (§3.8): 450 s de inactividad, sin pasar del fin de la oferta, y se regeneran solos al faltar, cambiar de formato o dañarse; si una invalidación se pierde, su copia puede quedar desactualizada hasta 10 minutos como máximo (el tope de edad), y el precio de oferta que se cobra sale de esa copia.
- **Los Términos de Servicio (`/terminos`) son un texto de primera versión que conviene revisar.** Describen lo que el sistema hace hoy, pero las consecuencias de una reventa confirmada (retirar publicaciones, restringir o suspender la cuenta) son un derecho que TiendaYa se reserva: lo único automático es la suspensión **temporal** por un hallazgo de confianza alta (§3.11, PLAN §20); retirar publicaciones o una suspensión duradera no tienen mecanismo y son decisión humana. Sus Términos (v1.2) describen esa suspensión temporal, la vigilancia con límites suaves, el tope de pedidos por hora y que los productos de un vendedor suspendido se ocultan. El pedido guarda *cuándo* aceptó el vendedor, no *qué versión* de los términos; si el texto cambia, esa constancia no distingue versiones. El registro público tampoco pide aceptarlos: solo se pide el compromiso al comprar.
- **La suspensión automática actúa sobre el nivel «alta» de un detector, que no es una prueba** (§3.11, PLAN §20): compartir un buzón ya es «alta», así que una pareja con una bandeja común se suspende hasta que alguien la revise. Sus límites conocidos: el primer barrido es **retroactivo** (suspende de golpe lo que ya tenga un hallazgo alto, aunque sea de hace meses); la suspensión es de toda la cuenta (sus productos y ofertas flash se ocultan mientras dura, §21); **falla abierto** si Redis no responde; la persona suspendida **no puede pedir una revisión** desde el sitio; el plazo (24 h) no escala con la reincidencia; y a los administradores no se les avisa de una suspensión nueva más que en la propia sección.
- **La respuesta escalonada y el tope de pedidos son frenos, no una prueba** (PLAN §21). Los topes son **por cuenta**, no por persona ni por tarjeta: varias cuentas los reparten, y a esas las atrapa la señal D *después*; la ventana de pedidos por hora es **fija** (una ráfaga en el borde de dos ventanas puede duplicar el tope); viven en las **rutas HTTP**, así que una ruta nueva que cree pedidos tiene que ponerles `controlPedidos`; el contador de intentos de contraseña es por cuenta, de modo que quien tenga solo el token de otra persona puede dejarla sin pedir 15 minutos; la vigilancia **encarece** el fraude, no lo impide (se compra hasta el tope); el barrido es **retroactivo también para lo «posible»** (un hallazgo de hace meses limita hoy, como a Ana y a Luis); y, como todo lo demás, **falla abierto** si Redis no responde.
- **La señal de reventa (G, §3.11) compara títulos, no piezas físicas.** El catálogo no tiene un código de producto compartido entre vendedores, así que quien cambia una palabra deja de coincidir y quien vende algo genuinamente parecido puede salir como `posible`; es un candidato para revisión humana. No ve la reventa fuera de TiendaYa. El compromiso solo existe en las compras posteriores al cambio: los pedidos anteriores no tienen constancia, y no se les inventó una.
- **No hay forma de crear cuentas `vendedor`/`administrador`** desde el registro público — es a propósito (evita que cualquiera se autoasigne un rol con privilegios). Por ahora esas cuentas se crean a mano o por el seed.
- **No se puede recategorizar un producto** ni editar/borrar categorías, subcategorías o atributos ya creados.
- **El panel de ventas no es un gestor de pedidos** — agrega métricas para administrador; `GET /api/compras` sigue devolviendo los pedidos del usuario autenticado. No hay una vista de administración de pedidos de todos los compradores.
- **Cobertura de verificación parcial:** se conservan scripts de checkout, carrito, ofertas y recomendaciones. La incorporación analítica agrega `test:ventas`; ejecutar ese comando no sustituye la validación completa de integración, cuyo estado se registra en §3.10.
- **Crear/editar un producto escribe en MySQL y Mongo sin una transacción conjunta** — cada base queda consistente *dentro de sí misma*, pero no hay garantía atómica entre ambas. `crear()` intenta una compensación de mejor esfuerzo (si falla el paso de Mongo, se borra la fila de MySQL ya creada), pero no es una solución completa — esa es explícitamente tarea de Entrega 3. Ver [ADR-002 §5](ADR-002-migracion-catalogo-documental.md).
- **Lo que ocurre mientras una base está apagada no siempre se pone al día solo** (ENTREGA-3-CONSISTENCIA.md §7.6): la copia de stock de Mongo sí se repara sola al volver, pero lo que no llegó al grafo de Neo4j o al índice de Elasticsearch se recupera con `npm run fraude:backfill` y `npm run busqueda:backfill` (idempotentes). Con Redis apagado no rigen los topes de pedidos ni los bloqueos de cuentas (ya eran «falla abierta» por diseño). Con Mongo apagado se compra usando el índice de búsqueda para saber si un producto está publicado.
